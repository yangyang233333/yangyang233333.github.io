**RDMA 绕过的主要是数据传输的内核快路径，不是资源管理的全过程。** 数据还没发出去，内存注册、队列创建或状态修改就可能失败；只看交换机计数器，未必能解释这种错误。

RDMATracer 关注的正是这个位置：在 RDMA 控制路径里，用有选择的 eBPF 探针保留能够解释失败的证据，而不是追踪每一次数据收发。

> 资料边界：本文基于论文摘要、作者在 FOSDEM 2026 和 NANOG 97 的公开材料，以及 Linux 官方文档与固定版本源码。尚未取得论文 PDF，因此不作全文复述或完整实验评估，也没有复跑作者的性能测试。下文会区分公开设计、源码核对和自己的工程建议。

## 一、这里的 syscall，不是每发一个包就调用一次内核

`libibverbs` 提供的是用户态 API，不能把一个 verb 简单等同于一个独立的 Linux 系统调用。

资源管理等慢路径经由 `/dev/infiniband/uverbsN` 与内核交互，具体接口可使用 `ioctl` 或 `write`；建立好资源后，许多快路径操作则直接访问映射到用户态的硬件资源，不需要每次进入内核。

因此，需要把两类问题分开：

- **数据路径问题**：通信是否拥塞、丢包、超时，吞吐和时延是否异常。
- **控制路径问题**：MR 能否注册、QP 能否创建或修改，内核与驱动是否正确完成资源设置。

RDMATracer 的公开设计主要针对后者。如果应用只报告“注册内存失败”，但真正的错误发生在驱动调用的某个内核辅助函数里，应用日志只能告诉我们出口处失败了，不能告诉我们错误从哪里开始。

## 二、扩展性首先来自少追踪，而不是更快地记录一切

作者讲稿给出的一个重要选择，是先收窄调用路径，再讨论探针机制。其剪枝规则可以概括为：

| 公开讲稿中的选择 | 对观测范围的影响 |
| --- | --- |
| 避开只读查询路径 | 不把所有查询都纳入常驻详细追踪 |
| 避免深入纯内核辅助函数 | 把重点放在与目标资源状态相关的边界 |
| 避开清理和引用计数路径 | 缩小这类故障诊断所需的追踪范围 |
| 按硬件厂商选择驱动路径 | 不同时追踪所有厂商的实现 |

这不是“这些函数不会出错”的证明，而是针对诊断目标做出的取舍。如果目标换成资源泄漏或清理失败，照搬同一组剪枝规则就可能漏掉最需要的证据。

在机制上，讲稿比较了 `kretprobe` 与 `fexit`，并采用后者观察函数返回时的参数和结果。但“某种探针更快”不能替代范围设计：给大量无关函数安装低开销探针，仍可能比少量有诊断价值的探针昂贵。

我的理解是，应该先问：**为了区分几类常见失败，最少需要观察哪些函数边界？** 而不是先把整个调用图录下来，再希望离线分析能解决一切。

## 三、正常路径计数，异常路径保留细节

下面是按公开讲稿整理的简化示意，不是原图或可直接部署的实现：

```text
NCCL / libibverbs
        |
        v
  uverbs / driver ----- resource setup -----> RNIC
        |
     eBPF probes
        |
        +---- selected calls ----> per-CPU counters
        |
        +---- error context -----> ring buffer
                                        |
                                        v
                                userspace analysis
```

讲稿中的计数覆盖调用次数、失败次数和错误码维度，错误上下文经 ring buffer 交给用户态处理。两者回答不同的问题：计数用于判断某类错误是否正在增加，详细事件用于解释一次失败发生在哪条路径上。

**程序常驻，不等于把每次成功调用的完整上下文都导出。** 这种分离把常见路径的工作压缩到较轻的统计，把更昂贵的记录和分析留给值得诊断的事件。

另一个细节是保留成功基线。作者讲稿描述了周期性采集正常 trace，再与失败 trace 比较、寻找分叉位置的流程。它让诊断从“这个错误码是什么意思”，推进到“同一类操作为什么走到了不同的分支”。

不过，返回值判定必须遵守被追踪函数的契约，不能对所有内核函数统一使用 `retval != 0`。有的接口用正数表示成功结果，有的返回指针；即使确实返回错误码，也可能是预期中的能力探测结果。讲稿就提醒，某些被禁用的功能会按预期返回 `ENOENT`。

所以，**采集异常、认定作业失败、触发告警，是三件不同的事**。这也解释了为什么用户态还需要结合调用语境处理事件。

## 四、一个历史案例：为什么“权限错误”可能来自返回值错配

作者讲稿介绍过一个案例：应用调用 `ibv_reg_dmabuf_mr` 时收到 “Operation not permitted”，追踪随后把问题缩小到 `ib_umem_dmabuf_map_pages` 与 `dma_resv_wait_timeout` 之间的返回值不匹配。

为了理解这个机制，可以独立核对公开的 Linux 历史版本，而不依赖厂商驱动的内部实现。

在主线 Linux **v5.19** 中，`dma_resv_wait_timeout` 返回 `long`：负值表示错误，零表示等待超时，正值表示成功。它内部以超时预算初始化返回值，没有需要等待的 fence 时也可能直接返回这个正值。

同一版本的 `ib_umem_dmabuf_map_pages` 返回类型却是 `int`，在等待 fence 的分支直接返回上述函数的结果；上层又把它当作“零成功、非零失败”的状态码使用。

这里同时存在两个问题：**位宽收窄，以及返回值语义没有转换。** 下面只演示前者：假设来自常见 64 位 `long` 环境的一个大正数，被解释为有符号 32 位整数。

```python
import ctypes

remaining_timeout = (1 << 63) - 1
narrowed_return = ctypes.c_int32(remaining_timeout).value
print(remaining_timeout > 0, narrowed_return)
```

输出是 `True -1`。原来为正的值，在这个窄化示例里变成了 `-1`。如果后续按负错误码传播，就可能表现为权限类错误，而不是实际发生了权限检查失败。

即使某个正数没有变负，也不能原样交给“非零即失败”的调用方。真正需要修正的是接口契约，而不只是换一个更宽的临时变量。

对照主线 Linux **v6.1**，相应代码使用 `long` 接住结果，然后明确转换：负值继续返回，零转换为 `-ETIMEDOUT`，正值转换为成功状态 `0`。这个对照仅说明公开历史版本中的机制变化，不推断作者厂商分支的完整补丁，也不表示当前内核仍存在同样的问题。

这个案例体现了内核追踪的价值：**不仅看到最外层报错，还能检查错误沿调用链传播时，是否改变了原本的含义。**

## 五、借鉴这套设计，还需要补上哪些约束

以下是我的工程建议，不是对 RDMATracer 已实现功能的声明。

1. **给观测系统本身做计数。** Linux BPF ring buffer 空间不足时，预留记录会失败，而不是等待消费者腾出空间。部署类似方案时，应单独统计记录失败、消费积压和上报失败，避免把“没有事件”误读成“没有故障”。
2. **让成功基线可比较。** 至少区分内核版本、驱动版本、设备类型和关键调用参数。否则两条 trace 的差异可能来自配置不同，而不是故障。
3. **分开衡量几种成本。** 探针运行时间、用户态解析与上报成本、应用端到端性能不是同一个指标。不能把单次探针的微基准结果直接当成整套系统的生产开销。
4. **保留其他诊断通道。** 返回探针要等函数返回才触发，不能单独覆盖永久阻塞或崩溃；故障需要入口时间、超时检测或崩溃日志时，应增加对应信号。控制路径追踪也不能代替网络遥测。

RDMATracer 最值得借鉴的，不是“把 eBPF 放进 RDMA 系统”这个动作，而是围绕故障语义选择观测边界。控制路径失败不自动等于网络拥塞：先找到失败发生、传播或被误解释的位置，再决定需要补哪一层证据。
